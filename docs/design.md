# 工作原理

## 设计目标

一个性能分析工具如果本身就拖慢服务器，就不该常驻。因此本模组把「常驻巡航」与「按需深潜」分成两套机制，用完全不同的手段实现。

| 层 | 手段 | 开销 | 用途 |
| --- | --- | --- | --- |
| 区块热度 | 上下文采样 | 低于 wall time 的 0.001% | 常驻，找出嫌疑区块 |
| 对象明细 | JFR 作用域事件 | 每个被检查对象约 40 纳秒 | 按需，精确到对象 |
| 方法采样 | JFR 栈采样加时间戳归并 | 与上一层共用插桩 | 按需，精确到方法 |

## 区块热度

服务器线程在每个 ticking 对象处只做一件事：发布「当前正在 tick 哪个区块、属于哪类工作」。它**不计时**。

一个独立线程以约 1000 Hz 读取这个字段。某区块被采样命中的比例，就是它占用 tick 时间的比例。这在统计上等价于计时，但便宜三个数量级。

发布使用 `VarHandle.setOpaque`。这是既能禁止 JIT 提升或消除写入、又能保证采样线程最终可见的最弱访问模式。刻意不用 volatile：此处不需要与任何其他内存建立顺序关系，而在弱序 CPU 上 opaque 可以省掉一道屏障。

采样间隔带有随机抖动。固定速率会与服务器固定的 50 毫秒 tick 周期相位锁定，反复落在每个 tick 的同一位置，从而系统性地扭曲结果。

### 两层保留

历史分两层，因为排行只需要「每个区块占多少比例」，而比例就是计数。

| 层 | 覆盖 | 存储 |
| --- | --- | --- |
| 原始样本 | 最近 5 分钟 | 每个样本 21 字节的定长环形缓冲，约 6 MB |
| 聚合桶 | 最近 6 小时 | 每 10 秒一桶，桶内按区块计数 |

老样本没必要逐个保留：到达时直接计入当前桶，回答的是同一个问题。节省来自热点的集中性——一秒采到一千个样本，但通常只落在几十个区块上，桶里存的是每区块一条而非每样本一条。实测 6 小时的聚合桶通常只占约 1 MB，同样时长若保留原始样本需要 445 MB。

封桶后改用并列的原始类型数组而非映射：一个百来条的映射，对象头开销数倍于内容本身，而桶有数千个。

窗口不超过 5 分钟时由原始层精确回答，更长的由聚合层回答。两层实测排名一致，误差在零点几个百分点以内。

## 对象明细

对选中的区块，用一个 JFR 自定义事件包住每个 ticking 对象的执行。

选择 JFR 而非手写计时器有两个理由。事件自带精确时长，直接回答「这个漏斗花了多久」；事件与栈采样由 Flight Recorder 打上**同一时钟**的时间戳，这是下一层归因的前提。手写 `nanoTime` 成对计时成本相同，却只能满足前者。

插桩点先判断目标区块，再去取对象类型与坐标。因此检查运行期间，区块外的每个对象只付出一次比较。

检查默认限时 30 秒。时长到点后立即停止插桩，但录制会多保持数秒，以收下已在途中的事件。

## 方法级采样

从外部采样一个线程，无法得知它当时在处理哪个区块。跨线程抓栈在本项目参考机上实测耗时 5516 纳秒，这段时间里服务器线程已经走过好几个对象。这条路走不通。

可行的做法是时间戳归并：对象 tick 事件与栈采样由 JFR 打上同一时钟的时间戳，于是只需判断某个样本是否落在本区块某个对象的时间窗内。无需时钟校准，也无需原子捕获。

验证结果：

| 平台 | 采样器 | 归并结果 | 实际热点 | 未归因 |
| --- | --- | --- | --- | --- |
| Windows 11 | `jdk.ExecutionSample` | 2143 / 309 | 2142 / 307 | 5 / 2457 |
| Linux | `jdk.CPUTimeSample` | 270 / 42 | 270 / 42 | 0 |

### 采样器选择

`jdk.CPUTimeSample` 来自 JEP 509，按 CPU 时间而非墙钟采样，不受 safepoint 偏倚影响，是更准确的选择。但它**仅 Linux 可用**。

陷阱在于：该事件类型在 Windows 上**同样被注册**，`FlightRecorder.getEventTypes()` 查得到，启用也不报错，然后一个样本都不产，只在 stderr 留下一行 `CPU time method sampling not supported in JFR on your platform`。

因此可用性判断必须同时检查操作系统，仅检查事件类型存在与否会得到一个静默失败的分析器。实测对照：

| | Windows 11 | Linux |
| --- | --- | --- |
| 类型已注册 | 是 | 是 |
| 5 秒内样本数 | 0 | 312 |

两个事件的配置方式也不同。`jdk.ExecutionSample` 用 `withPeriod`，`jdk.CPUTimeSample` 用 `throttle`；线程字段分别叫 `sampledThread` 与 `eventThread`。CPU 时间采样的实际速率远低于请求的上限，因此报告一律给出样本数与占比，绝不宣称速率。

## 实测开销

参考机 JDK 25.0.1、Windows 11、16 核，基线扣除，循环带数据依赖以防被优化消除。

| 原语 | 开销 |
| --- | --- |
| `VarHandle.setOpaque` 写入 long | +0.03 ns |
| JFR 自定义事件，录制关闭 | 约 0 ns，JIT 完全折叠 |
| JFR 自定义事件，录制开启 | +40.0 ns |
| `System.nanoTime()` 成对 | +39.2 ns |
| `Thread.getStackTrace()` 跨线程 | 5516 ns |

关闭状态下的残留：

| 状态 | 每个 ticking 对象 | 折算 |
| --- | --- | --- |
| 从未启用过 | +0.002 ns | 字面意义的零，JIT 直接折叠分支 |
| 启用中 | +0.08 ns | 0.0016% |
| 启用后再关闭 | +0.08 ns | 0.0016%，JIT 不会退回 |

即关闭后每个对象残留一个完美预测的必不命中分支。

游戏内实测，`/wttl status` 自行报告：热路径低于服务器 wall time 的 0.001%，采样线程占单核 0.5% 至 1.2%，1000 Hz 请求下实际达成约 915 Hz。

## 插桩点

Fabric API 只提供整个世界层面的 tick 事件，没有逐对象的钩子，因此这部分必须用 mixin。全部为 HEAD 与 RETURN 回调，不重定向、不覆写、不取消，其他模组可以自由注入同样的方法。

| 目标 | 覆盖的工作 | 区块来源 |
| --- | --- | --- |
| `ServerLevel#tickNonPassenger` | 实体刻 | `entity.chunkPosition()` |
| `ServerLevel#tickChunk` | 随机刻与冰雪 | 参数直接给出 |
| `ServerLevel#tickBlock` | 计划方块刻 | `BlockPos` 换算 |
| `ServerLevel#tickFluid` | 计划流体刻 | `BlockPos` 换算 |
| `LevelChunk$BoundTickingBlockEntity#tick` | 方块实体刻 | `getPos()` |

方块实体插桩落在绑定 ticker 而非可重绑定的包装器上。包装器只做转发，两者都插会使每个方块实体被计两次。

以上取值全部读取缓存字段或做纯算术，插桩不产生任何分配。

## 归因语义与边界

- **只覆盖主服务器线程。** 区块生成、区域文件 IO、异步寻路运行在工作线程上，不计入
- **耗时算在 ticking 对象所在的区块。** A 区块的漏斗拉取 B 区块的箱子，耗时记在 A。这是正确且可操作的定义
- **排行中的百分比是占区块 tick 时间的比例**，不是占整个 tick 的比例。当服务器大部分时间花在区块工作之外时，同一个百分比对应的绝对毫秒数会小得多
- **历史最多保留 6 小时**，其中最近 5 分钟为原始精度。请求更长的窗口会返回现有全部数据并说明
- **自动抓取依据近 100 tick 的平均值**，因此抓得到持续劣化，抓不到瞬时尖峰。99 个 10 毫秒的 tick 中夹一个 500 毫秒的 tick，平均值仅 14.9 毫秒
- **Flight Recorder 不可用时**，对象明细与方法采样无法启动，区块热度不受影响

## 存档安全

- 只持有区块坐标的 long 键，不持有区块、实体或世界对象的引用
- 不写 NBT，不注册游戏规则，不加载区块
- 报告写入游戏目录下的 `whotickstoolong/`，与 `logs/` 平级

## 构建

```
./gradlew build
./gradlew runServer
```

必须使用仓库自带的 Gradle wrapper。系统安装的 Gradle 若低于 9.x 无法在 Java 25 上运行。

Minecraft 26.1 起官方不再混淆代码，构建方式与旧版本差异很大：

- 无 Yarn 与 Intermediary 映射，Yarn 停更于 1.21.11
- 插件 ID 为 `net.fabricmc.fabric-loom`，对应不做重映射的实现
- 依赖使用 `implementation`，不是 `modImplementation`
- 产物为普通 `jar` 任务，不是 `remapJar`，没有 refmap
